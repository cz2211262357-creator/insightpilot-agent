# 评测协议与验收证据

评测分为 **controlled 工程链路** 与 **online 真实模型**。两者都经过实际 LangGraph、MCP HTTP、PostgreSQL 只读查询、检查点和证据报告。控制供应商按预声明脚本回复，验证工程机制；它的通过率不作为真实模型准确率。

## 固定协议

`evals/gold_cases.json` 固定 20 题、参考 SQL、参数、指标及澄清答案。两个合成租户由种子 20261025 生成，数据快照 as_of 为 2026-10-07 UTC，业务日期按 Asia/Shanghai。G15/G16 明确为 2020 年 1 月空月份；G12 明确逐单展示本地支付时间。这些口径在首次在线评测前固定，不按模型回答改参考结果。

G04/G05/G06/G14/G15/G16/G18/G20 需要补充指标或时间，共 8 题。在线供应商只接收原问题、目录和预声明的用户澄清答案，不接收参考 SQL、预期数值或通过标记。最多自动填写两次澄清；意外高成本审批不会被评测器自动放行。

独立参考查询通过相同租户的只读 RLS 账号执行。结果比较忽略行顺序和列别名，允许整列重排，保留重复行及维度与数值对应关系；数值统一比较到小数后六位，NULL 与零不同，本地午夜日期与日期类型等价。实际结果被截断即不匹配。此规则最多六列，只适用于本套固定题，不等价于证明 SQL 语义对所有数据库都相同。

报告逐题保存终态、实际 SQL/参数/证据 SHA256、参考结果、澄清记录、指标计划匹配、持久调用预算及供应商返回的模型名称和用量。缺失 Token 保留 null；known_* 只是已知下界，只有全部调用完整上报才给 reported_* 总量。p50/p95 使用 nearest-rank，包含排队、执行及脚本确认耗时，不代表人工等待或公网多用户 SLA。

## 故障验收映射

| 场景 | 必须命中的证据 | 用例 |
| --- | --- | --- |
| P01 后台 A 切 B 后完成 A | 两个真实 Worker PID、B 获得前台容量、A 合法成功 | `test_two_real_worker_processes_preserve_foreground_capacity_and_background_topic` |
| P02 明确确认/重放/修改/撤权 | 专用 token、冲突或拒绝状态，普通聊天不批准 | `test_hitl.py`、`test_query_gateway.py` |
| P03 旧 Worker 防旧写 | 实际暂停/终止、执行版本递增、旧 checkpoint 提交为零 | `test_old_process_expired_lease_recovered_after_real_sql_old_checkpoint_zero` |
| 同池租户清理 | 同连接跨租户读取、无范围查询零行、恢复后仍 RLS | `test_rls_catalog.py`、`test_backup_restore.py` |
| 危险 SQL/提示注入 | 模型确实返回 DELETE、query_used=0、没有证据提交 | `test_topic_and_hitl.py` |
| 查询/整轮超时和预算 | 注入实际耗时或耗尽持久预算，明确终态且无伪成功 | `test_query_gateway.py`、`test_budget.py`、`test_execution_recovery.py` |
| Redis/MCP/数据库故障 | 暂停真实容器或断开连接，不能绕过准入或权限 | `test_health.py`、`test_mcp_http.py`、`test_execution_recovery.py` |
| 浏览器连接与多页面 | 真实浏览器两页面 CAS、历史恢复、原任务确认、导出、移动布局 | `tests/browser/check_workbench.py` |
| 环境跟踪隐私 | 强制开启外部 tracing 指向本机收集器，实际收到请求为零 | `test_release_hardening.py` |

测试里的暂停/恢复有显式命中点。租约故障用例会只修改本次拥有的测试任务时钟/租约，不能将它描述成等待了完整 60 秒。真进程退出与真实 Redis/PostgreSQL 都经过执行。后台并发验证与数据问答匹配是不同指标。

## 实测记录

控制模式已执行 20 题完整链路，20 题证据结果匹配，8 个指定澄清均中断后恢复；68 次控制模型调用与 20 次实际 SQL 查询。控制 Token 为固定夹具数据，不是供应商账单。

真实模型使用百炼 `qwen-plus`，数据为固定种子的合成经营数据。每轮各运行一次，题目、标准 SQL 和数据版本相同：

| 实测指标 | 首轮 | 第一轮优化后 | 第二轮优化后 |
| --- | ---: | ---: | ---: |
| 报告完成 | 5/20 | 16/20 | 20/20 |
| 证据结果严格匹配 | 2/20 | 14/20 | 19/20 |
| 完整流程通过 | 0/20 | 13/20 | 16/20 |
| 需要澄清的 8 题中实际发起澄清 | 1/8 | 6/8 | 6/8 |
| p50 / p95 耗时，秒 | 13.046 / 24.516 | 15.422 / 35.000 | 18.891 / 39.969 |
| 供应商报告的 Token 总数 | 81,073 | 125,021 | 133,818 |

完整流程通过指任务成功、查询证据和指标匹配，并且预先要求澄清的题目确实完成过澄清。首轮的 2 题证据虽然匹配，但没有按约定澄清，所以完整流程是 0/20。第一轮优化引入受限的输出格式纠正、粒度校验、文本安全处理与分阶段提示；本次样本中调用次数和耗时也增加了。

第二轮未达完整通过的四题中，两题结果匹配但未按协议澄清销售额口径；一题查询证据匹配但计划未列出全部预期指标；一题返回了正确的订单编号和金额，但额外返回字段，因此不满足预先规定的严格列数匹配。以上情形均按预设规则如实计为未通过，没有在评测后调整参考答案或比较规则。

这 20 题参与过优化迭代，结果是工程回归记录，不是独立留出集上的泛化准确率；单轮耗时也不是生产 SLA。用户应检查生成的 SQL、数据版本和报告证据，系统不能保证所有自然语言问题都被正确理解。
